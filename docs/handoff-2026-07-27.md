## Deploy rules — read before doing anything

- **NEVER `git push` without Karl typing the literal phrase "Deploy Live"** (or
  an unmistakable equivalent). Committing freely is fine and expected.
- Deploy is `git push origin main` — this branch must be merged first.
- **`prisma.config.ts` points `datasource.url` at PRODUCTION** (`DIRECT_URL`).
  A bare `prisma db push` / `prisma migrate` / `migrate diff --from-migrations`
  writes to prod. Always `npm run db:push:dev`, and hand-write migrations.
- `db:push:dev` writes **no migration file**, and prod deploys with
  `migrate deploy`. A pushed-but-unmigrated column silently does not exist in
  production. This already bit us once (`20260726170000_trainer_schedule_view_prefs`).

### Prod checklist when it does deploy
1. `npx dotenv -e .env -- npx tsx scripts/backfill-addon-billing-items.ts` —
   events, puppyschool and memberships have **no BillingItem row in prod**, and
   `TrainerAddon.itemId` is an FK to it, so toggling any of them 500s.

## Traps that have already cost hours

- **e2e specs share ONE seeded database and one trainer.** A spec that mutates
  shared state (a persisted preference, an invoice's description) must restore
  it in `afterAll`, or it silently breaks a *later* spec. `scheduleView` made
  previously-independent specs order-dependent this way.
- **Paid add-ons are never seeded.** A spec for a gated page then reads the
  Add-ons redirect instead of the page — which looks exactly like a tenancy
  leak (a cross-tenant test reading 200 instead of 404). Two false alarms so
  far. Seed a `BillingItem` + `TrainerAddon` (see `global-setup.ts`).
- **A `vi.mock` factory replaces a module wholesale.** Omit a constant the code
  reads at module scope and the whole test file dies at import, before a single
  test runs.
- **Specs can silently SKIP** when the seed has nothing to act on — a green
  suite is not proof they ran.
- **Background agents die with their session.** A session limit killed six
  mid-edit and left ~90 half-written files. Commit early.
- **`git commit` takes the whole INDEX, not just the paths you added.** With
  several agents working at once, `git add <your-path>` then `git commit` will
  sweep up anything a colleague had already staged. This happened twice tonight:
  the multi-ticket-enrolment feature (schema, migration, lib, route, UI, three
  test files) is committed under `4649a1d "feat(forms): one editor for every
  kind of form…"`, and the memberships rename is buried in the WIP checkpoint
  `5c9a7b3`. Nothing was lost, but neither is findable by its message. Use
  `git commit -- <path> [<path>…]`, which commits ONLY those paths regardless
  of what else is staged.
- **Don't `rm -rf .next` or `npm run build`** while Karl's dev server is up on
  port **7777** — it breaks his running app.
- `next build` typechecks; `vitest` only transpiles. A type error can hide from
  the unit suite and still fail CI.

## 1. Preview banner covering content — DONE

`src/app/(client)/preview-banner.tsx`, `src/app/(client)/layout.tsx`.

The bar was `sticky top-0 z-50`. Three separate faults, all measured in a real
browser at 390px and 1440px rather than read off the CSS:

- The shell's phone brand bar (`app-shell.tsx`, ClientShell) is **also**
  `sticky top-0`, at z-30. On any scroll both parked at y=0 and the banner
  covered the header completely — trainer logo and account button hidden and
  untappable.
- The desktop sidebar is `md:fixed md:inset-y-0`, so its logo row sat under the
  banner **even at rest** (measured: sidebar top 0, banner 0→61; the logo was
  simply not on screen — see the before/after screenshots described below).
- `layout.tsx` "compensated" by adding `2.75rem` to `--app-safe-top`. That did
  nothing: the CLIENT shell never reads that variable (only the trainer shell
  and settings-tabs do), the banner actually measured **61px** not 44px, and
  the comment called it "a fixed bar" when it was sticky.

Fix: the banner is now genuinely `fixed`, with a **stated** height — the content
row is pinned to `h-11` instead of being whatever padding produced, so the
offset is arithmetic: `calc(2.75rem + 1px + env(safe-area-inset-top, 0px))`.
A scoped `<style>` block (keyed off `.pm-preview-shell` on the layout wrapper,
so it can only ever apply in preview) pushes the shell down by that amount and
re-tops the two pieces of chrome that pin themselves to the viewport.

Measured before → after (headless Chromium, safe-area 0):

| | before | after |
|---|---|---|
| banner height | 61px, `sticky` | 45px, `fixed` |
| desktop sidebar top | **0** (logo covered) | 45 |
| phone header top, scrolled | **0** (fully under the banner) | 45 |
| `/my-availability` content top, 1440 scrolled | **0** (under the banner) | 45 |

`--app-safe-top` override removed from `layout.tsx`. The intake-gate branch
(which renders the banner without the AppShell) got the wrapper class too, so
it is offset as well.

⚠️ **The selectors in that `<style>` block are structural** — they match
`.pm-preview-shell > div:last-child > aside` and
`… > div:last-child > div > header`, i.e. ClientShell's own layout. If anyone
restructures `ClientShell` in `src/components/shared/app-shell.tsx` (not my
file), those two rules stop matching and the banner starts covering things
again. `tests/e2e/preview-banner-offset.spec.ts` measures the geometry and will
catch it.

## 2. Events + memberships on /my-availability — DONE

**Events were never missing.** They were being listed as "Group classes" (the
wizard's `openRuns` query had no event filter), and the ticketed one was quoted
at the **package price**. On Karl's dev data: "Puppy Social — one-off" showed
**$45** while selling **$200 / $123 / $89** tickets. That is the d736544
undercharge reproduced on the client side — and it was also unbookable, because
`/api/my/classes/[runId]/enroll` now 400s a ticketed booking with no
`ticketTierId`.

Now: events are split out with `isOneOffEventPackage` into their own type
("Events", PartyPopper icon), with a step-2 ticket picker (tier radio list with
per-tier remaining + a quantity stepper clamped to the tier's remaining and to
`MAX_TICKET_QUANTITY`), and the POST carries `ticketTierId` + `quantity`.

The money rule lives in one pure, unit-tested place —
`src/lib/client-wizard-events.ts` `toWizardEvent()`: **`priceCents` comes back
`null` whenever the offering has any ticket tier**, so there is nothing for the
UI to quote by mistake. The list shows "from <cheapest tier>", never the package
price. Verified live: list → picker → confirm all quote $200 for General entry,
CTA reads "Pay $200 & book". Un-ticketed events keep the package price and the
ordinary FULL enrol path (including the multi-dog picker; ticketed events don't
get one, because a ticket is a place and the API bills tickets, not dogs).

**Memberships were invisible because of data + a deliberate filter.**
`loadPublishedMemberships` filtered `cadence: 'ONE_OFF'`, and the demo trainer's
only published membership ("Juniors") is RECURRING — so the "Packages" tile
never rendered at all. Recurring plans now load too, priced per period
("$400.00 / month") and flagged `buyable: false`.

`layout.tsx:216` hiding `/my-memberships` from the client nav **is intentional**
— both that comment and `my-memberships/page.tsx`'s own comment say memberships
moved inside Offerings in commit 347cc12, and the page survives as the Stripe
return target. Left as-is. It does mean the booking screen is the only way in,
which is exactly why the tile had to start showing.

## 3. "Request this" for packages that can't be bought — DONE

Karl's follow-up: the dead-end sentence became an action.

- New model `MembershipRequest` (+ `MembershipRequestReason`
  RECURRING/NO_PRICE, `MembershipRequestStatus` PENDING/FULFILLED), migration
  `20260727140000_membership_requests`. **Applied to the dev DB via
  `npm run db:push:dev`. NOT applied to prod** — it ships with the deploy
  (`build` runs `prisma migrate deploy`).
- `POST/DELETE /api/my/memberships/[membershipId]/request`. Deliberately mirrors
  the shop's `/api/my/products/[productId]/request`: same PENDING row, same
  idempotency, same trainer-in-preview carve-out.
- **Notification: `CLIENT_SHOP_ORDER`, no new type.** It is the only existing
  type whose documented meaning is "a client bought **or requested** one of your
  products", it carries a free-form `detail`, and its default body
  (`{{clientName}} {{detail}}.`) renders correctly. The two reasons read as the
  different jobs they are: "asked about the ongoing plan “X” — it needs setting
  up" vs "asked about “X” — it has no price yet". The one wart is the default
  title prefix, "Shop — {{clientName}}"; trainers can edit it in
  Settings → Notifications.
  - Rejected `Enquiry`/`NEW_ENQUIRY`: an Enquiry is prospect-shaped and its
    Accept flow **creates a client**. These requests come from people who
    already are clients, so accepting one would be wrong.
- Guarded: a package checkout *would* take is refused with 409, so Request can
  never be used to skip paying. Add-on gated and tenant-scoped like the buy
  route.
- `requested` is read back from the row by `loadPublishedMemberships`, so
  "Requested — your trainer will be in touch" survives a reload. The button uses
  the same `resolveButtonColors` treatment as the buy button.

Verified live end-to-end on the dev DB: initial "Request this" → click →
"Requested…" → reload still "Requested" → repeat POST returns 200
`alreadyRequested: true` with still exactly one row. Test rows were deleted
afterwards; Karl's demo data is back as it was.

⚠️ **There is no trainer-side screen listing these requests.** The trainer gets
the notification and nothing else — no inbox, no badge, no "3 clients want
Juniors". The trainer memberships screens are not mine, so I did not build it.
**This is the biggest open gap in the feature** and should be the next piece.
